# 重启协议：什么时候能重启，怎么保证能回来

这份文档给使用本插件的 Agent 看。工具 `restart_now` / `wake_register` 已经把下面大部分判断做进代码，但**什么时候该重启**仍然需要模型判断。

---

## 一句话

重启会让当前回合立即中断。所以顺序永远是：**判定没人阻塞 → 登记唤醒 → 挂计划任务 → 本回合收尾 → 重启 → 醒来验收**。顺序错了，任务就丢了。

---

## 第 1 步：先看有没有会话真的在跑

`restart_status` 会列出运行中的会话。判定规则：

| 情况 | 判定 |
|---|---|
| running 且**没有**唤醒登记 | 真阻塞，不能重启 |
| running 但**已登记**（它写好待办去等了） | 不算阻塞，继续 |
| 全部 idle | 可以重启 |

空闲会话重启后能恢复，不算「有活在跑」。

`restart_now` 默认就按这条规则拦截，返回 `status: "blocked"` 并列出阻塞方。只有确认可以打断时才传 `force: true`。

## 第 2 步：有活在跑时，二选一

**等**：**先**用 `wake_register` 登记自己（写唤醒文件），**再**挂一条重检提醒（`schedule_create`，**默认 300 秒即 5 分钟**，较急可缩短到 60 秒）。顺序不能反：只挂提醒不登记，别人在等待期间触发重启时不会叫醒你，提醒又可能在重启中丢失。等待期间不要反复探活、不要反复试重启。登记过的会话，别的会话会当作「已收尾」。

**转**：改做不需要重启验证的事——读代码、写文档、跑测试。把「待重启」记在当天的工作日志里，等下一个窗口。

两条都不做、硬闯，是最容易丢工作的做法。

## 第 3 步：没人阻塞 → 自主执行

前置检查通过后直接做，不要再问一遍「要不要现在重启」——问了等于把决定推回给人。

`restart_now` 会依次：

1. 检查重启互斥锁（`restart.lock`）：
   - 不存在 → 继续；
   - 存在且 ≤10 分钟 → 返回 `busy`，说明别人正在重启，**不要再挂一个**；
   - 存在且 >10 分钟 → 视为上次失败，清掉重来。
2. 检查阻塞会话（见第 1 步）。
3. 写唤醒登记 `wake-pending-<sessionId>.json`。
4. 写重启参数 `restart-config.json`。
5. `schtasks /Create` + `/Run`，约 12 秒后 Harness 退出并重启。

**重启必须是本回合最后一步**：回复、日志、记忆都写完再调用。工具一返回，倒计时就开始了。

### 重检通过后，先清提醒再重启

等待期间挂的重检提醒，重启后仍然存在。如果不清掉，它会在新进程里再次到点触发——轻则多跑一轮检查，重则再发起一次重启。

`schedule_edit({ id, action: 'delete' })` 对 **active 和 inactive 都有效**（DSH 0.2.2 起 `schedule_delete` 已移除），难点只在拿到 id：`schedule_list` 只列未触发的，已触发的必须按 id 删。所以：

1. `schedule_create` 时**记下返回的 id**（0.2.2 起还需 `target: 'this_session'`，时间用 `rrule` 两行：`DTSTART;TZID=Asia/Shanghai:YYYYMMDDTHHMMSS` + `RRULE:FREQ=DAILY;COUNT=1`）；
2. 确定可以重启时：`schedule_edit({ id, action: 'delete' })` → `restart_now`；
3. 重启后醒来：**再按同一个 id `schedule_edit({ id, action: 'delete' })` 一次**，把已结束的记录也清掉——这一条对「等待中、被别人唤醒」的会话同样适用：它醒来后第一件事就是删自己的重检提醒，再继续。

> 一般性的定期提醒（例如每日简报）不要删；只删为这次重启临时挂的重检项。

---

## 第 4 步：重启后发生了什么

新进程启动 → 本插件延迟 3 秒 → 扫描登记目录 → 用 `sessionController.prompt` 逐条投递（会**自动 resume 冷会话**）→ **投递成功后直接删除登记文件**：成功不落盘，日志里留一行 `delivered`。只有损坏、过期、重复才归档，且只保留最近 10 个；`wake.log` 超过 256 KB 会轮转为 `wake.log.1`。

同时插件会清掉 `restart.lock`：新进程活着，就说明上一次重启已经结束。

没有登记时完全静默，只写一行 `no-pending` 日志。

---

## 第 5 步：醒来后必须验收

1. 读重启日志 `wake.log` 或脚本日志，确认末尾 `RESULT: OK`；
2. 从**新的**运行时上下文取 Web GUI 端口并确认服务活着（端口每次重启都会变）；
3. 用 `restart_status` 确认：锁已释放、登记已消费（成功不留文件）、可执行文件路径仍有效；
4. 如果重启前后改了配置，确认改动已生效。

验收通过后再继续干活。**不要重复重启**：日志已经有 `RESULT: OK` 就说明上次成功了。

## 已知的坑（都踩过）

| 坑 | 现象 | 原因 / 对策 |
|---|---|---|
| 在 Harness 内 `Start-Process` 启动重启脚本 | 日志停在 `killing` 就不再往后 | Harness 把子进程放进 Windows Job Object，杀 Harness 时脚本一起被杀。**必须走计划任务** |
| 杀完立刻启动 | 新实例启动后马上退出 | Electron 单实例锁还没释放。脚本会多等 3 秒 |
| 先杀渲染进程 | 听得到 Windows 报错音，看不到弹窗 | 浏览器进程把渲染进程死亡当成崩溃并弹原生错误框。**先杀浏览器主进程**再杀子进程 |
| `sessionController.prompt(request)` 只传一个参数 | `Cannot read properties of undefined (reading 'throwIfAborted')` | 第二个参数 `signal` 是必需的 |
| 用 `schtasks /Query /TN <名字>` 判断权限 | 报「找不到文件」，误以为被安全策略拦了 | 任务本来就不存在。先跑全量 `schtasks /Query /FO LIST` 再判断 |
| 重启后立刻再重启一次 | 双重启、会话被砍两次 | 先读日志确认 `RESULT: OK` |
| 唤醒登记写在重启之后 | 重启后再写，已没有进程读它 | 登记必须**先于**挂任务 |

---

## 安全边界

- 工具只投递文本，不执行任意命令；
- 每条登记最多投递 3 次，失败归档，绝不无限重试；
- 登记超过 24 小时自动过期，避免昨天的残留今天乱弹；
- 互斥锁防止两个会话同时挂任务；
- 可执行文件与脚本在动手前校验，缺一个就不重启。

---

## 跨平台说明

- **唤醒**：纯 Node，跨平台可用；
- **重启**：依赖 Windows `schtasks` 与 PowerShell，仅 Windows；
- 非 Windows 上 `restart_now` 会直接报错，不会做任何破坏性动作。
